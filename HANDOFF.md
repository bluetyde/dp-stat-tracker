# Handoff: Light mode

Written for a fresh session to pick up — no code was changed while writing this, everything below was confirmed by reading the current files (paths/line numbers as of this writing; re-check if they've drifted). Codebase is at v0.8.0 and has grown a lot (map layout pictures, round-result classification with save-round stars, per-round kill marks, live player count, tie handling, DPL rating) — don't assume anything from an older summary is still current.

## The real scope — read this before starting

This is **not** a small "add a few CSS overrides" task, and it's important not to underestimate it starting out. The app has exactly one theme today, defined as 12 CSS custom properties in `electron/theme.css`'s `:root` block (`--bg`, `--bg-raised`, `--bg-tile`, `--border`, `--border-soft`, `--text`, `--text-bright`, `--text-muted`, `--text-faint`, `--accent`, `--accent-bright`, `--accent-dim`, `--loss`, `--loss-bright`) — but **most of the app's actual colors don't route through those variables at all**. They're literal hex/rgba values written directly into inline `style=` attributes and into `<style>` blocks inside `hub.html` and `overlay.html`. Confirmed counts, current as of this writing:

- `hub.html`: 56 `rgba(...)` calls, ~30 distinct hardcoded hex colors, both inside its big inline `<style>` block and scattered across individual elements' `style=` attributes throughout the body.
- `overlay.html`: 6 `rgba(...)` calls, plus its own inline `<style>` block.
- `hub-renderer.js`: 2 hardcoded hex colors (small, but they exist — `#e28a42`, `#2b353f`).
- `theme.css` itself: 19 hardcoded hex colors *outside* the `:root` block (the `:root` variables get reused correctly in some rules, but plenty of other rules in the same file hardcode their own values instead of referencing a variable).
- `scoreboard-view.js` (the shared row-rendering JS used by both the overlay and the Hub's Match Detail panel): **zero** hardcoded colors — it only sets `className`, and the classes it references are defined elsewhere. This file itself needs no changes; the classes it points at do.

**The decision that has to be made explicitly, not defaulted into silently**: do you (a) migrate every one of those hardcoded colors to CSS custom properties first, so a `[data-theme="light"]` override block on `:root` correctly cascades everywhere — the *correct* fix, but touches a large number of individual `style=` attributes across two big HTML files — or (b) add a narrower `[data-theme="light"]` block that only overrides the 12 existing `--*` variables, and accept that everything still hardcoded (badges, tags, prediction bars, role indicators, delete buttons, etc.) will **not** respond to the toggle and will look wrong or illegible against a light background until migrated separately. Option (b) is faster to ship but will visibly look broken/inconsistent the moment someone actually flips the toggle and looks at more than the Home page. Recommend (a), scoped incrementally (get the shared/high-traffic surfaces — Match Detail, Home, nav — fully migrated first, rather than trying to do the whole app in one pass).

## Specific things already confirmed, worth knowing before touching anything

- **No existing toggle, no persistence mechanism, no `prefers-color-scheme` usage anywhere in the codebase.** Grepped for all of `prefers-color-scheme`, `data-theme`, `lightMode`/`darkMode`, `localStorage`, `electron-store`, `nativeTheme`, `systemPreferences` — zero matches. This is a from-scratch feature, not extending a half-built one.
- **Two separate windows, two separate renderer processes**: `overlay.html`/`overlay-renderer.js` and `hub.html`/`hub-renderer.js` are genuinely separate `BrowserWindow`s (see `main.js`'s `createOverlayWindow`/`createHubWindow`). If the theme choice should apply to both (almost certainly should — a Hub in light mode and an in-game overlay still in dark mode would be a strange, probably unwanted mismatch), **plain `localStorage` won't sync between them** — each window's renderer has its own isolated storage. Persisting the choice in the main process (a small JSON file, same pattern `match-archive.json`/`map-layout-library.js`'s `index.json` already use) and broadcasting it to both windows via IPC on change is the safer approach, not a per-window `localStorage` value. Decide this deliberately; don't let it default to "only the Hub remembers, overlay forgets on every launch."
- **Some of the color-coded UI is functionally meaningful, not just decorative** — win/loss/tie/save-round coloring exists specifically so those states are visually distinguishable at a glance (see `.result-win`/`.result-loss`/`.result-tie` in `theme.css`, and `.match-map-card--win`/`--loss`/`--save` in `hub.html`). `.result-win`/`.result-loss`/`.result-tie` already correctly reference `var(--accent)`/`var(--loss)`/`var(--text-muted)`, so they'll pick up a `--accent`/`--loss` override automatically — good, no extra work needed there specifically. But don't just literally invert the dark palette's lightness values for a light theme: the current `--accent` (`#7fb6e8`, a light pastel blue) and `--loss` (`#d1565e`) were chosen for contrast against a near-black background (`--bg: #0d1013`) — used as-is against a white/light background, they may not have enough contrast to read clearly, especially at the small font sizes this UI uses throughout (many `font-size: 10-13px` labels). Pick new light-mode values for contrast against the new light background, not just reuse the dark ones.
- **`.role-badge--attack`/`.role-badge--defense`/`.role-badge--unknown`** (added this session, in `hub.html`'s own `<style>` block, ~line 328) hardcode their own colors (`#f4848d`, `#84c0f4`) rather than referencing variables — these are a concrete, findable example of exactly the kind of thing that needs migrating, not an edge case to worry about later.
- The `--font-display`/`--font-body` variables are typography, not color — untouched by this, no action needed there.

## Suggested order

1. **Decide the persistence architecture first** (main-process-backed JSON file + IPC broadcast to both windows, per above) — this affects how the toggle UI itself gets wired, so get it settled before writing any CSS.
2. **Design the light palette** — 12 new values for the existing `--*` variables, checked for contrast against a light background, not a mechanical inversion. Verify contrast on the smallest text sizes actually used (grep `font-size:` across `hub.html`/`theme.css` for the real range in use, don't assume).
3. **Add the toggle** — somewhere in the Hub's sidebar (near the version label added this session, `#appVersionLabel`, would be a reasonable spot) that sets `data-theme` on `<html>` and persists via the mechanism from step 1.
4. **Migrate the highest-traffic hardcoded colors first**: `hub.html`'s inline `<style>` block (Home page, Match Detail, Maps, Weapons, Played With), then `overlay.html`, then the rest of `theme.css`'s hardcoded rules. Grep-verify progress as you go (`grep -oE '#[0-9a-fA-F]{3,8}' hub.html | sort -u` should shrink toward zero, or toward only values that are deliberately theme-invariant).
5. **Verify live in both windows**, not just the Hub — launch the real app, toggle light mode, check the overlay during an actual or archived match (win/loss coloring, KAST/HS%/FF DMG columns) and the Hub's Match Detail view (round cards — win/loss/tie/save must all stay visually distinct, kill-mark reticles from this session must stay visible against the new card backgrounds) in both themes side by side. Don't just eyeball the Home page and call it done — that's the one view most likely to already look fine while everything else is still broken.
